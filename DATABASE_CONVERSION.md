# MySQL schema conversion

`Schema_Metadata.json` was converted into Laravel migrations and Eloquent artifacts for the configured MySQL database. The conversion includes 52 metadata tables, 49 foreign keys, 162 indexes (including primary keys), 64 check constraints, 15 enums, three views, and the source trigger hooks.

## Schema and type mapping

MySQL has one active database schema per connection, so the PostgreSQL namespace is preserved in each physical table name: `auth_users`, `public_bookings`, `storage_objects`, `vault_secrets`, and `supabase_migrations_schema_migrations`. `schema_migrations` is present in both `auth` and `supabase_migrations`; those tables use separate Eloquent models (`AuthSchemaMigration` and `SupabaseMigrationsSchemaMigration`).

| PostgreSQL type or feature | MySQL/Laravel representation |
| --- | --- |
| `uuid` | `CHAR(36)`; Laravel UUID models generate IDs with `HasUuids` |
| `text[]` | JSON arrays |
| `json` / `jsonb` | MySQL JSON |
| PostgreSQL enum types | MySQL `ENUM` with the metadata values |
| `timestamp with/without time zone` | `DATETIME`; MySQL has no per-value time zone storage |
| `bytea` | `LONGBLOB` |
| `inet` | `VARCHAR(45)` |
| PostgreSQL sequence on `auth.refresh_tokens.id` | MySQL auto-incrementing `BIGINT` |
| schemas | schema-prefixed table names in the same MySQL database |

The migrations use JSON expression defaults and enforced check constraints. Use **MySQL 8.0.16 or newer**; JSON expression defaults require MySQL 8.0.13+, and earlier MySQL versions parse but do not enforce `CHECK` constraints. Indexed PostgreSQL `text` columns and text-based foreign-key identifiers are represented with bounded `VARCHAR` columns to keep full `utf8mb4` indexes within MySQL key limits and ensure matching FK types.

All declared primary/unique keys and foreign keys are retained. The 13 partial unique indexes use nullable generated columns for their predicates where needed; nullable generated values allow multiple nonmatching rows. Nonunique partial indexes are represented as full indexes, which preserves index coverage but not the original filtering optimization.

## Laravel artifacts

Each metadata table has an Eloquent model, migration, factory, and seeder. Models use the prefixed physical table name, the declared primary key, appropriate casts, UUID behavior, and `belongsTo` plus inverse `hasOne`/`hasMany` relationships for the 49 foreign keys. Migration order follows the foreign-key dependency graph. `DatabaseSeeder` invokes table seeders in that order.

Laravel's default `users` and `sessions` tables remain separate from imported `auth_users` and `auth_sessions`. The database session user key and Sanctum polymorphic token key are UUID-compatible with the imported `auth_users.id`. `.env` credentials were left intact; `config/database.php` now defaults to MySQL when `DB_CONNECTION` is unset.

## Views, triggers, and source limitations

The JSON contains 14 trigger declarations but not the PostgreSQL function bodies they call. They are represented by 23 MySQL triggers (multi-event triggers and derived defaults are split into separate triggers). MySQL equivalents were added for timestamp updates, auth-user profile creation, booking/feature-request notifications, competition-booking validation, and competition participant counts. PostgreSQL's multi-event triggers were split into separate MySQL triggers. The notification recipients and competition participant-count rules are conservative interpretations of the trigger names and table metadata; compare them with the original function bodies before relying on exact business behavior.

The two `pg_stat_statements` views are empty compatibility views because MySQL has no equivalent PostgreSQL extension data. `vault_decrypted_secrets` preserves the view shape but returns `NULL` for `decrypted_secret`: the snapshot omits the Vault decryption function implementation and key material, so exposing the stored ciphertext as plaintext would be incorrect. Vault nonce generation uses `RANDOM_BYTES(24)` on MySQL; on MariaDB versions without that function, the SQL trigger derives 24 bytes from UUIDs, while Eloquent `Secret` writes use PHP's cryptographically secure `random_bytes(24)`.

The metadata only says which tables had row-level security enabled; it contains no policy expressions. MySQL has no PostgreSQL-style row-level security, so those flags cannot be enforced as database policies from this input. No policies were invented.

PostgreSQL UUID defaults are generated by Laravel's `HasUuids` model behavior. Direct SQL inserts that omit UUID primary keys must provide the UUID themselves. The `identities.email` derived default is preserved by a MySQL insert trigger.

## Runtime verification

`php artisan migrate` completed successfully without resetting or dropping data. `php artisan db:seed` completed in dependency order; seeders fill each metadata table to at least five rows without reseeding rows already present. Runtime verification found all 52 imported tables populated, all 49 foreign keys free of orphan rows, and all three compatibility views plus 23 triggers installed. PHP syntax checks passed across migrations, seeders, factories, and models.

The active Laravel connection uses the `mysql` driver, and the local server reports `10.4.32-MariaDB`. It successfully ran this MySQL-compatible implementation. A production Oracle MySQL instance should use MySQL 8.0.16 or newer as described above.
